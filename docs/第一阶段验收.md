## 旧历史完整性

真实测试前，以 SQLite 只读连接逐条计算原有消息和关键会话字段的指纹。第一轮联调完成、进一步旧接口抽查前的核对结果如下。

| 数据范围 | 原有会话 | 原有消息 | 消息改动或缺失 | 关键会话字段改动或缺失 |
| --- | ---: | ---: | ---: | ---: |
| 默认 profile | 342 | 19,356 | 0 | 0 |
| feishu-ws profile | 28 | 1,536 | 0 | 0 |

检查包含原消息全部数据库字段，以及会话标题、来源、消息与工具计数、父会话、归档和置顶字段。新增消息和新增会话单独计数，不要求数据库文件整体哈希相同。

随后在旧接口抽查及版本升级期间，原基线检测到 10 条旧消息的全字段指纹差异，没有消息或会话缺失、没有关键会话字段变化。源码确认完整消息 HTTP GET 会执行 `_ensure_display_order` 并回填显示索引；其中 3 条通过原始指纹重构确认只涉及 `display_identity` / `display_order`。其余 7 条不凭哈希推测原值，也不把这段跨版本记录描述为“所有字段完全未变”。没有进行整库回滚或直接写库修补。

因此完整历史改用官方 `SessionDB(read_only=True)` 和 SQLite `query_only`。读取子进程禁止惰性安装，启动时检查读取能力；读取失败不回退到可能写入索引的完整历史接口。真实读取旧会话分别返回 47 和 32 条消息，已解码的旧图片内容块也通过受控引用展示。

用户升级至 0.23.0 后另建独立基线。最终复验和部署后，该基线的 **374 条会话、20,905 条消息** 全字段指纹及关键会话字段均无新增改动或缺失：默认 profile 为 346 条会话、19,369 条消息，feishu-ws 为 28 条会话、1,536 条消息。

留存基线位于服务器 `/tmp/hermes-haven-phase1-close-audit-01a1aece.json` 和 `/tmp/hermes-haven-023-readonly-baseline-01a1aece.json`，可重构记录位于 `/tmp/hermes-haven-phase1-derived-originals-01a1aece.json`。2026-11-06 提交前再次通过 SQLite 只读连接复核：升级后基线的 20,905 条原有消息无改动或缺失；升级前基线仍有 10 条差异，其中 3 条仅显示元数据变动的重构验证通过。

## 复验命令

常规检查：

```shell
go test ./...
go vet ./...
npm --prefix web test
npm --prefix web run build
```

有 C 编译器的 Linux 环境可执行 `go test -race ./...`。真实测试必须显式启用，会向 Hermes 添加新的独立验收会话；默认 `go test ./...` 跳过该测试：

```shell
HAVEN_LIVE_HERMES=true HERMES_ENV_FILE=/root/.hermes/.env go test -run TestLiveHermesPhaseOne -v -timeout 6m .
```
